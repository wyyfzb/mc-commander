## 一、P0 · 上线门槛（不修不能称可交付）

### 安全类

**S-P0-1 `/auth/setup` 首访设密无所有权证明（公网抢注接管窗口）**
- 证据：`routes/auth.js:81-97`——`isConfigured()` 检查与 `setPassword()` 之间无凭证要求、无事务保护，服务绑定 `0.0.0.0`（`index.js:154`）。
- 风险：部署完成到管理员设密之间，任何发现端口者可先设密永久接管面板；并发请求存在 TOCTOU 竞态。
- 方案：setup 要求携带 `.env` 中 `API_KEY` 或部署脚本打印的一次性 setup token；检查+写入放入 better-sqlite3 单事务。

**S-P0-2 升级接口 `mcVersion` 未校验 → 路径穿越 + 实例变砖**
- 证据：`routes/upgrade.js:23-25` 仅非空校验；`upgrade.service.js:283-284` 拼接 `server-${mcVersion}.jar` 写入路径，`L65/L85` 拼入上游 URL。
- 方案：路由层白名单 `/^\d{1,3}(\.\d{1,3}){0,3}$/`；`newJarPath`/`backupJarPath` 复用 `resolveSafePath`；`jarFile` 入库同样校验。

**S-P0-3 登录失败锁定按 `req.ip` 计数，`trust proxy=1` 下 XFF 可伪造绕过**
- 证据：`index.js:105` 无条件信任代理；`routes/auth.js:30-32` 用 `req.ip` 作锁定键，`loginFailures` Map 无容量上限。HTTP 限流已用 `socket.remoteAddress`（`rate_limit.js:17-19`），两处标准不一致。
- 方案：登录锁定改用 `req.socket.remoteAddress` 对齐限流器；`loginFailures` 加 LRU 上限；`trust proxy` 改为环境变量可配。

**S-P0-4 Webhook URL 无内网/回环限制（SSRF 打内网 + 读回响应体）**
- 证据：`routes/webhooks.js:20-27` 仅校验 http(s) 协议；`webhook.service.js:119-134` 投递 3 次重试且响应体（4096B）落库可读回。
- 方案：DNS 解析后拒绝私网/回环/链路本地 IP（防 rebinding）；默认仅 https；投递日志不存响应体。

**S-P0-5 RCON 固定 `rcon.port=25575` 且 `server-ip=` 空 → 全网卡暴露 + 多实例冲突**
- 证据：`routes/server-jar.js:132,157,161` 部署生成的 properties 中 RCON 端口不随实例派生。
- 方案：`rcon.port` 按实例派生（同 server-port 模式）；文档强制防火墙封锁 RCON 端口段。

### 交付类

**D-P0-1 版本号五处失真，更新检查机制实际失效**
- 证据：`package.json:3`(0.1.0) vs `index.js:156`(v1.1.0) vs `mc_commander_server/README.md:5`(1.1.0) vs `routes/index.js:25,57,68`(硬编码 0.1.0) vs `SHA256SUMS.txt`(v1.0.0)；仓库 0 个 git tag；「检查更新」对比 npm 上不存在的包名 `mc-commander-server`。
- 方案：版本单源化（package.json 注入 /health、check-update、启动横幅、前端 `__APP_VERSION__`）→ 建 CHANGELOG.md → 走一次 tag 流程验证 release.yml 全链路。（1-3 天）

**D-P0-2 无日志系统：无级别、无文件、无轮转、无错误分离**
- 证据：全服务端仅 console.log/error；`config.js:17` 定义 `logLevel` 但零消费；nohup 分支产出无轮转 `server.log`。
- 方案：轻量结构化日志（pino 或 console 包装器），级别消费 config.logLevel，error 分流独立文件，20MB×5 轮转；systemd 场景文档说明用 journalctl。（1-3 天）

**D-P0-3 端口被占用 = 裸崩溃**
- 证据：`index.js:154` `server.listen` 未监听 `error` 事件，EADDRINUSE 输出原始堆栈后退出。
- 方案：捕获 EADDRINUSE 输出「端口 X 被占用，请修改 .env 的 PORT」后 `process.exit(1)`；顺带校验 MC 实例端口与面板端口冲突。（半天）

**D-P0-4 文档/UI 与交付物不符**
- 证据：引导页推销 Docker 卡片（`onboarding-page.tsx:22-23,174-192`）但无 Dockerfile 且 roadmap 明确不做；宣称 Windows 免安装包但 release.yml 只产 tar.gz；`mc_commander_server/README.md:33` 一键部署用 gitee `master` 路径而分支是 main（404）；手动部署文档缺「前端 dist → public/」整合步骤。
- 方案：删/灰置 Docker 与 Windows 卡片；master→main 修复；README 手动部署补前端产物整合说明。（半天）

**D-P0-5 无升级指引，存量部署无法安全更新**
- 证据：deploy 脚本支持重复执行升级（`deploy-mc-commander.sh:406-414`）但文档零提及；无 CHANGELOG；sha256 回写 PR 合并顺序未说明。
- 方案：README 新增「升级」章节（重跑脚本、保留项清单 .env/data/servers/backups、回滚方式、sha256 PR 先合并再公告）。（1 天）

### 前端类

**F-P0-1 全应用无错误边界，组件崩溃落入英文默认错误页**
- 证据：`main.tsx:25-43` 无 ErrorBoundary；`routes.tsx:79-126` 16 条路由均无 `errorElement`；事件处理器/WS 回调异常无人兜底。
- 方案：根路由+顶层路由补中文 `errorElement`（返回仪表盘/重试）；AppShell 包 ErrorBoundary；main.tsx 注册 `onerror`/`unhandledrejection`。（半天）

**F-P0-2 `McSocket.connect()` 非幂等 → 双 WebSocket、事件重复派发、连接泄漏**
- 证据：`api/ws.ts:88-89` 不检查旧连接直接 new；`use-server-socket.ts:186-197` effect 重跑即 connect；`degradation-banners.tsx:36` 重连按钮同样直调。
- 方案：connect 入口判断 `readyState <= 1` 直接返回既有 promise；重连前 `close()` 旧连接并清 reconnectTimer。（随 F-P0-1 后 1 天）

## 二、P1 · 重要（影响「放心交给普通用户」）

### 安全
- **S-P1-1** JAR 下载（部署/升级）无体积上限、无 sha256 校验（`server-jar.js:74-123`、`upgrade.service.js:94-131`）——对比插件市场已有 100MB 截断+域名白名单。方案：落地校验上游 sha256 + 512MB 流式截断 + 域名白名单。
- **S-P1-2** 弱 API Key 非生产仅告警不阻断（`index.js:70-75`），默认绑 `0.0.0.0`——方案：弱 Key 默认阻断或强制 `ALLOW_WEAK_KEY=1`；提供 `HOST` 变量默认 127.0.0.1。
- **S-P1-3** 无安全响应头（无 CSP/XFO/nosniff，全仓无 helmet）——方案：自实现 6 行安全头中间件；README 增 Nginx/Caddy 含 `/ws` upgrade 的 HTTPS 反代示例。
- **S-P1-4** WS 鉴权仅握手时执行，踢会话后长连接仍存活（`websocket.js:147-150`）——方案：30s 心跳周期内抽样复验会话，失败 `close(1008)`。

### 交付
- **D-P1-1** 面板自身数据库（mc_commander.db）零备份——方案：每日 `db.backup()` 快照至 `backups/panel/`，纳入现有保留策略。（1-2 天）
- **D-P1-2** `.env.example` 仅 12 项，config.js 实际约 20 项；`NODE_ENV` 未引导导致生产门控（弱 Key 阻断、错误掩码）默认失效——方案：补全+注释，加 .env 与 config 一致性测试。（半天）
- **D-P1-3** 无截图、无面向用户的图文文档（`README.md:14-16` 截图待补充）——方案：6-8 张核心页面截图 + 「首次使用 10 分钟」向导 docs/user-guide.md。（1-2 天）
- **D-P1-4** Windows 声称支持但 CI 全 ubuntu，better-sqlite3 原生编译未验证——方案：CI 加 windows-latest job 或 README 标注实验性。（1 天）

### 前端
- **F-P1-1** 会话令牌轮换后 WS 单例不重建，旧 token 永久占住实时通道（`use-server-socket.ts:53-57`、`ws.ts:75`）——方案：凭据不一致时 close+重建单例；登出时显式关闭。
- **F-P1-2** 备份面板/玩家表把「加载失败」渲染成「空态」（`backup-panel.tsx:172-193`、`player-table.tsx:487-491`）——方案：补 `isError` 分支复用 EmptyState+重试，对齐 instances 页规范三态。
- **F-P1-3** 文件上传静默同名覆盖（`files-page.tsx:331-341`）——方案：冲突中断+确认（对齐插件页 40912 流程）；危险扩展名/已存在文件 overwrite 确认。
- **F-P1-4** 文件编辑器切换文件窗口期草稿覆盖竞态（`files-page.tsx:127-134`）——方案：切换时清空 draft 置加载态，数据到达前禁编辑。
- **F-P1-5** oxlint 未启用 `react-hooks/exhaustive-deps`，12 处 disable 注释形同虚设——方案：开启该规则，逐条清理。

### UX
- **U-P1-1** 实例页启动不处理 EULA 首启——旅程①死亡谷：部署完成点启动得到无关报错（`instances-page.tsx:59-61` vs 仪表盘 `instance-controls.tsx:80-84` 已有特例处理）——方案：EULA 特例抽成共享 mutation，部署向导内置 EULA 同意+「部署并启动」闭环。（半小时，性价比最高）
- **U-P1-2** 启停无 starting/stopping 中间态，实例页与仪表盘行为不一致——方案：store 增 `phase` 字段，WS started/stopped 确认后清除；两处启停收敛同一 mutation。
- **U-P1-3** 崩溃触达三断裂：非当前实例崩溃事件被丢弃（`use-server-socket.ts:95`）、`circuit_breaker` 事件前端无通知映射、通知条目不可点击跳转——方案：critical 事件按实例广播入通知中心+「查看实例」跳转+持久 toast；补 `circuit_breaker` case。
- **U-P1-4** 审计页/命令历史功能孤岛（285 行页面已完整实现但无路由无入口 `routes.tsx` 未注册）——方案：注册 `/audit` 入侧栏。
- **U-P1-5** 备份入口过深（设置二级页）+列表硬截断 10 条无分页（`backup-panel.tsx:85-86`）——方案：仪表盘加「最近备份」卡+立即备份；列表总数+分页。
- **U-P1-6** 危险操作防护倒挂：卸载实例（删全部数据）仅单击确认，恢复备份却要输实例名——方案：卸载复用输入确认机制（ConfirmDialog children/confirmDisabled 能力现成）。
- **U-P1-7** 窄屏崩坏：玩家详情 `w-[420px]`、文件页三栏 `w-[220px]+w-[45%]` 零断点（`player-detail-panel.tsx:68`、`files-page.tsx:346,383`）——方案：<lg 玩家详情改 Sheet、目录树折叠抽屉、表格紧凑卡片行。

### 设计系统
- **DS-P1-1** 死 token 工具类 6 处（渲染 bug）：`text-mcs-text-secondary`×3（upgrade-dialog.tsx:141,157,162）、`bg-mcs-bg-card`×2（account-panel.tsx:80、login-page.tsx:228，登录卡无底色）、`text-mcs-base`×1（market-sheet.tsx:286）——方案：改正确 token + token-integrity 测试增「utility 拼写 ↔ @theme 注册表」校验防复发。（30 分钟+1-2h）
- **DS-P1-2** 原始调色板残留 20 处/4 文件 + emerald-600 白字对比度 3.77:1 不达 AA（`password-strength.ts:61-76`、`account-panel.tsx:212` 等）——方案：迁入 `--mcs-success/warning/error-*` 状态 token；补 `--mcs-fg-disabled`/`--mcs-divider` 缺口 token 消化 12 处跨类别借用。（半天）

## 四、评分与定位

**交付就绪度 64/100**（部署 14/20 · 配置 11/15 · 安全 10/15 · 可观测 8/15 · 文档 9/15 · 测试 8/10 · 更新 4/10）

- ✅ 可立即交付：Linux 进阶服主（会 SSH、读得懂中文、会看 journalctl），约目标用户前 30-40%
- ⚠️ 勉强：Windows 服主（start.bat 未经 CI 验证）
- ❌ 不可交付：普通小白用户（端口崩溃/无日志/无 HTTPS 引导会立即流失）、需要升级运维的存量用户

**安全成熟度**：内测→公测之间。修复 S-P0-1 + S-P0-2/3/5 且弱 Key 默认阻断后可评「公网部署就绪」。

**体验成熟度**：可用 9/10 · 好用 6/10 · 惊喜 7/10。🔴 修复后进「好用」档；惊喜路径=崩溃自动诊断卡片+全局活动中心。

**设计系统**：token 化 9/10，复用率约 85%。全部长尾漂移 2-3 个工作日可清零。
