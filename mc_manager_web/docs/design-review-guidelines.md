# 前端设计审查指南

本文档记录前端代码审查中的设计规范守门规则，供 Agent 交叉审查与 PR review 使用。

> 设计基准（P1-P6 原则、设计文档章节索引、工具链路径）由 owner 私有维护，不随仓库分发；
> 本文档只覆盖下列可机械判定的守门规则，以及无法机械判定、只能靠审查口径统一的边界
> （着色来源边界、反馈级别三级口径、字号档位适用面）。

## 字号档位适用面（2xs 的中文边界）

**规则**：`text-mcs-2xs`（10px）只用于**可扫读的角标、单位、短标签与 mono 元数据**；
**完整句子最低 `text-mcs-xs`（12px）**。

- 合规面（保持 2xs）：徽章计数、列头词（「事件」「严重度」「站内」）、短标签（「默认」
  「即时生效」「未保存」）、数量单位（「{n} 种可用」「今日新增 {n}」）、IP / 耗时 / 坐标等
  mono 元数据、以单位收尾的省略式状态行（「连接正常 · 延迟 12ms」）。
- 越界面（提到 xs）：提示语、错误说明、帮助文本、任何完整句子——
  例「事件类型加载失败，无法勾选事件」「规则修改保存后即时生效，无需重启实例」。
- **判据是「短语 vs 句子」，不是「有没有中文」**：列头「严重度」正确，句子「保存后关闭本提示，
  页面只显示剩余可用数量。」越界。灰区兜底：**含 `，／；／。` 分句标点、或中文 ≥15 字者按句子处理**。
- **只判可见文本**：`title=` / `aria-label` 里的句子不计（它们不进视觉密度）；
  变量、三元表达式与数据驱动的文案（如 gamerule 的描述串）要看**渲染结果**，按行文本扫描看不见。
- **无门禁**：长度/标点只是代理量，精度不足以做静态拦截（`check-design-tokens.mjs` 不扫这条）；
  由交叉审查与 PR review 按本口径把关。`ui/` 目录豁免静态字号门禁，但仍受本规则约束。
- 依据：CJK 笔画在 10px 下屏显发糊，12px 才是中文正文的常规下限；`semantic.css` 的 2xs
  定义处指向本节。

## CTA 配额

每页最多 **1 个绿色实底 CTA 按钮** + **outline 变体 ≤ 2 个**。

- 绿色实底 CTA（`variant="default"` 的 Button）用于页面唯一主操作，如「保存」「提交」。
- outline 按钮（`variant="outline"`）用于次操作，同一页面不超过 2 个排布。
- **判定域一：顶栏常驻不计。** 全局外壳（顶栏 / 侧栏）里跨页面常驻的 outline 按钮
  （如顶栏搜索入口）不是「某一页的次操作」——它不随该页内容增减，也不参与该页的操作分级。
  配额只数**页面内容区**的按钮。
- **判定域二：随条目重复的行内按钮不计。** 列表 / 网格里逐条目渲染的行内按钮
  （如每张实例卡的「停止」「切换」）数量由数据条数决定，不是排布决策的结果。
  它们按**条目内**的操作分级判定（每个条目内次操作 ≤2），不按整页合并计数——
  按页计数会随 N 线性膨胀、失去约束力（实例页：稳态 3、N=3 时 6，而每张卡始终只有 2 个）。
- **判定域三：覆盖层内独立计数。** 弹窗 / 抽屉 / 命令面板（`ui/dialog`、`ui/sheet`、`ui/popover`
  承载的全屏或浮层面）内的按钮按**该覆盖层自身**计数（≤1 绿色实底 CTA、outline ≤2），
  不与宿主页面内容区合并。理由：覆盖层打开时页面内容被遮罩、不在同屏竞争；
  但它自身仍需唯一主操作。**不豁免**——「不合并」不等于「不计数」。
- **判定域四：状态驱动的告警条动作不计。** `NoticeBanner` 一类**由运行态条件渲染**的告警条内，
  那个「解除该告警」的动作按钮不计入 CTA 配额（它随告警存在，不是排布决策的结果——
  否则「连接断没断」会决定页面按钮数）。但它仍须遵守「危险语义色只从变体取」：
  改用统一的危险浅档变体 `destructive-outline`，不得手写色类。
  边界：**恒常渲染**的工具条 / 页头按钮不适用本豁免（那才是排布决策）。
- **同一操作行允许不同级。** 同一条操作行里危险项与中性项**不必统一分级**：
  后果不同的操作做成同一级反而抹掉信息（实例卡操作行：「停止」＝中断服务，走实底 `destructive`；
  「切换」＝导航，走中性 `outline`）。硬约束只有一条——**危险项一律走变体档，
  不得回到调用点手写 error 色类**：手写色类绕过了变体的唯一声明源，下一次调整危险色时会静默掉队，
  而对比度门禁只看 token 定义、结构上发现不了。
- 筛选开关 / 分段控件的**选中态**用 `variant="selected"`（淡底 + 强档描边 + accent 文字，
  与 `Chip` 选中态同口径），不计入 CTA 配额；禁止用 `variant="default"` 表示选中——
  实底渐变 + 辉光会让一屏出现多个发光绿按钮，主操作失去唯一性。
- `variant="destructive"` 不计入 CTA 配额（危险操作独立分级）。
- `variant="ghost"` / `variant="link"` 不计入配额。

## 圆角守门规则

业务代码**禁止**使用 `rounded-[...]` 任意值，必须使用设计 token（`rounded-lg`、`rounded-md` 等）或 `--mcs-radius-*` 变量。

### 豁免清单（shadcn/ui 基础组件）

以下 `rounded-[...]` 用法属于组件级派生，已在各组件文件头部注释标注豁免理由：

| 组件 | 模式 | 豁免理由 |
|------|------|----------|
| `scroll-area.tsx` | `rounded-[inherit]` | Viewport 继承父容器圆角，无法用 token 表达 |
| `input-group.tsx` | `rounded-[calc(var(--radius)-Npx)]` | 内嵌按钮/键盘需比容器圆角小 Npx 视觉内嵌 |

注：checkbox（`rounded-mcs-xs`）与 tooltip 箭头（`rounded-xs`）已改用 token/内置档，不再需要豁免。

审查新 PR 时，`components/ui/` 下新增的 `rounded-[...]` 需确认属于上述派生模式或补充豁免理由；`features/` 下任何 `rounded-[...]` 均应驳回。

### 扫描面边界（上表为何不含 `ui/` 的 5 处同形写法）

`ui/` 下同形写法实为 5 处：`ui/button.tsx` 4 处（`xs` / `sm` / `icon-xs` / `icon-sm`，形如
`rounded-[min(var(--radius-md),10px)]` 与 `…,12px)]`）＋ `ui/select.tsx` 1 处
（`data-[size=sm]:rounded-[min(var(--radius-md),10px)]`）。它们**不在**门禁第 5 条（脚本头部规则清单
第 5 条「`rounded-[` 任意值」）的判定面内——第 1–11 条逐行检查整体排除 `src/components/ui/`
（`check-design-tokens.mjs` 的 `EXCLUDE_DIR`），其余条目则都不判该形状（如第 12 条只收
`*-mcs-*` / `*-glass-*` 形状的类名），故既不会报错、也无需列入上表。此处仅登记扫描面边界，
不追认其理由；若将来把 `ui/` 纳入扫描面，需先为这 5 处补豁免条目并说明派生模式。

## 非语义 identity 色族（实例固定色相标识）

`--mcs-identity-1..6` 是**非语义**色族，只回答「是哪个实例」：**非语义 identity 色族，禁用于状态、告警、语义表达**。

- 槽位来源与类名映射的唯一入口是 `src/lib/instance-hue.ts`（实例 id 稳定哈希落 6 槽）；
  消费点只调该模块，不得在 feature 里再写第二份「哈希 → 类名」映射。
- 槽位**不落库**（instances 表无 color 列），跨端不涉及，服务端不参与着色。
- 本族与维度三色（`--mcs-dimension-*`）同属「非语义领域色」：领域色只标识**是什么**，
  不得被借去表达状态或告警。

### 与 `components/mcs/tone.ts` 的分工边界

| | 语义色（`tone.ts`） | identity 色（本族） |
|---|---|---|
| 回答的问题 | 「现在怎么样」——运行/停止、告警、成败、选中/激活 | 「是哪一个实例」 |
| 声明源（唯一） | `components/mcs/tone.ts` | `src/lib/instance-hue.ts` |
| 允许的形状 | 三件套（border + bg-subtle + fg）、accent 选中强调、图标底块、徽章、通知气泡 | 只作小图形填充（8px 色点 / 2px 色条） |
| 禁止的形状 | 半透明内容面 tint；弱档描边承担「已选中」信息 | **不承载文字、不做容器底**（故本族没有 `-fg` / `-bg-subtle` 档） |
| 同屏关系 | 可与 identity 标识同屏共存（实例色条 + 状态点/语义徽章） | 不得替代语义色表达状态，也不得被语义色替代作实例标识 |

判断口径：**色块回答「是什么」→ identity；回答「怎么样」→ 语义色**。
实例名的区分始终由文字承担，identity 色只是辅助标识，故它不承担文字对比度口径，只按
WCAG 1.4.11 非文字图形 ≥3:1 校验（`npm run check:contrast` 已覆盖 identity 六槽 × 七个面 × 明暗两主题，
实测暗色最差 6.88:1（identity-1 on bg-emphasis）/ 亮色最差 4.85:1（identity-4 on glass-overlay））。

门禁第 11c 条（手写 accent 选中强调形态）不覆盖本族，**与扫描面无关**（声明源
`src/lib/instance-hue.ts` 本就在 `src/` 扫描面内）：该条按**整词**匹配
`border-mcs-accent-border-strong` 与 `bg-mcs-accent-bg-subtle` 的同处共现，而本族只产出单一
`bg-mcs-identity-N` 填充类，结构上不进该判定面；同一原因也使它不参与第 9–10 条的角色矩阵
（`bg-mcs-identity-*` 落 `unknown` 而不被判定）。

### 色相定档：两态各有各的最优偏移

色相按「与既有九个色锚点（状态六色 + 维度三色）的最小角距」定档——色相相同、只靠彩度区分时，
8px 色点会被读成状态色。两个主题的锚点是**两套色值**（亮色 `--ref-*-light` 的色相整体偏移过，
如 warning 84°→46°），因此**两态的等距 60° 最优偏移不同，必须分别定档**：

| 主题 | 6 槽色相 | 最小角距 | 最近的一对 |
|---|---|---|---|
| 暗色 | `10 / 70 / 130 / 190 / 250 / 310` | **12.22°** | identity-1 vs `--mcs-error-fg` |
| 亮色 | `15 / 75 / 135 / 195 / 255 / 315` | **12.25°** | identity-5 vs `--mcs-info-fg`（亮色档） |

暗色最优偏移 ≈9.70°（最小角距 12.52°）、亮色 ≈15.14°（12.38°）；实取 10° / 15°——两态都落在
「最优值 −0.3° 以内」。定档只对着**暗色**色相表调参会让亮色侧退化：亮色沿用 10° 偏移时最小角距
只有 **7.25°**（identity-5 vs 亮色 info，OKLab ΔE 0.024，属「并排才分得出」），改任何一态前都要**两态分别复算**。

角距是主判据，但要清楚它的边界：identity 的彩度刻意压得比锚点低（暗 C 0.09 / 亮 C 0.10
对锚点 0.11-0.24），所以与最近锚点的 OKLab ΔE 主要来自**彩度差**而非色相差——
例如亮色 identity-5 与 info 的 ΔE 0.030 里，色相贡献只占一部分。也就是说「色相拉开」解决的是
「一眼认成同一个色」，而**同屏语义**（色点挨着语义色文字）必须靠布局解决，不能只靠调色相。

### 容量边界

6 个实例落 6 个槽，**恰好全部互不相同**的概率是 `6! / 6^6 = 1.54%`——即 **6 个实例时有 98.5% 的概率
至少两个同槽**（同槽即同色）。

- 本标识承载的全部信息就是颜色，**撞槽即失效**（不是「略有歧义」，是两个实例看起来完全同色）；
- 因此 identity 色**只作辅助辨认，不承担唯一性**：区分实例的责任在**实例名文字**上，
  任何依赖「颜色能唯一指认实例」的交互（如仅凭色点让用户选择实例）都不成立；
- 6 槽是「够用就好」的档位数，不主张扩容：槽数越多，槽间色差越小，可辨识性反而下降。

## 交互悬浮只走覆盖层（内容面 tint 不得当 hover 用）

**规则**：`hover:` 位置上只允许交互覆盖层 token（`--mcs-state-hover`、`--mcs-state-pressed`、
`--mcs-state-focus`，以及危险族的 `--mcs-state-hover-error`）；**不得**把内容面 tint
（`--mcs-*-bg-subtle`）放到 `hover:` 上。

- **为什么**：`*-bg-subtle` 是为「承载文字/图标的常驻面」设计的不透明 tint，它的有效色
  已经和基面算过一次；拿它当 hover 态等于让常驻面互相替换，宿主底色被整块换掉而不是
  叠一层——与 `--mcs-state-*` 那套「任何宿主上都成立」的覆盖层语义不是一回事。
- **危险族的例外形态**：中性 `state-hover` 叠在危险按钮上只「变亮」，读不出「更危险」，
  所以单开了 `--mcs-state-hover-error`（暗 16% / 亮 12%，取同档 `state-hover` 的 2×）。
  需要升温语义时走它，**不是**回到 `error-bg-subtle`。
- **为什么基座曾经破例**：`ui/button` 的 `destructive-outline` 变体一度写的是
  `hover:bg-mcs-error-bg-subtle`，四个调用点逐字照抄。基座是「危险按钮配方的唯一声明源」，
  它破例等于把违规量产——故修必须从基座改起，只改调用点会立刻被再抄回去。
- **无门禁**：现网已清零，但缺静态拦截，会随新危险行内按钮复发（已登记待办）。
  审查时扫 `hover:bg-mcs-` 后接 `-bg-subtle` 即命中。

## 反馈级别三级口径（瞬时确认 → toast → 常驻 NoticeBanner）

**判据是两问**——第一问定级别，第二问查能否满足。分级不看事件「重不重要」、不看操作「危险不危险」。

**第一问（定级别）：要反馈的对象是持续状态，还是瞬时事件？**（即：它指向的状态在事件结束后是否继续存在）

| 级别 | 载体 | 适用条件 |
|---|---|---|
| 1 瞬时确认 | 控件自身态变化（按钮 `disabled`/spinner、开关翻转、行内文案） | 结果**自身持久可见**于触发它的控件，且没有需要逐次告知的失败面（典型：本地即时保存的偏好开关） |
| 2 toast | `sonner`（`main.tsx` 的单枚 `Toaster`） | **一次性事件**的回执：完成 / 失败 / 已复制一类的「动作已受理或已成事」；事件过去后界面上不留痕 |
| 3 常驻 `NoticeBanner` | `components/mcs/notice-banner.tsx` | 状态**跨事件存续**、需用户反复可见或据以行动（本仓实例：`gamerule-panel.tsx:177`「gamerule 修改需要 RCON 连接」、`:182`「无法解析 gamerule 列表」、`plugins-page.tsx:301` 页头「启停与增删在重启实例后生效」） |

- 状态**继续存在** ⇒ **级别 3 是要求**，不是可选项。若该状态同时由控件态自我呈现，则是
  「级别 1 的控件态 + 一处级别 3 常驻说明」的组合，**仍不得省掉常驻说明**。
- 状态**不继续存在** ⇒ 级别 2；控件自身已足够且无失败面 ⇒ 级别 1。

**第二问（查能否满足）：是否存在可见的常驻载体？**
- **存在** ⇒ 按级别 3 落地。若该载体已由页面既有常驻说明承担（例：插件页页头
  「启停与增删在重启实例后生效」），则动作本身只需级别 2 回执，不必再加一条横幅。
- **不存在**（典型：保存即关闭的 dialog 内部）⇒ 这是**「未满足的级别 3 要求」，必须显式登记为缺口**：
  写清当下承担它的临时手段（如把口径写进 toast 文案本身）与将来的解决方向。
  **不得**反过来据「载体不存在」把级别 3 判为「不成立」——判据定在级别，载体只决定「现在能否满足」。

### 本仓现状与缺口登记

- **「重启待生效」类状态在本仓没有常驻载体**：它由 `instances/components/instance-settings-dialog.tsx`
  「保存后即关闭」的 dialog + 几秒即散的 toast 文案（`启动配置已保存，重启实例后生效`）承担。
  ⇒ **已登记的已知缺口**：状态真实存续，却无可见常驻物，用户可能在重启前忘记自己改过启动配置。
- **解决方向**（本轮未实现）：在实例页页头或启动配置入口给一处可见的「有待生效改动」常驻提示。
  它需要状态跟踪（保存即置位 / 重启即清除 / 跨刷新持久化与旧存储迁移兼容），属**新能力**而非
  反馈级别口径统一，已登记为**「功能级新能力池」候选**。

### 与单枚 Toaster 现状的关系

`main.tsx` 只有一枚 `top-center` 的 `Toaster`：级别 2 的成功与失败**同位置、同视觉权重**
（不按 severity 分色或分位置），分级完全由文案承担。这是已登记的取舍（见下），
本口径不要求为此新增第二枚 Toaster 或按 severity 改色——那会引入 token 体系外的颜色并与
`npm run check:contrast` 冲突，同时破坏「只有一个地方看反馈」的契约。

### 已登记的取舍（不改代码，仅登记）

- **成功与失败同权重同位置**：93 处 error 与 8 处 `duration: 1500` 的 success 共用同一枚 Toaster，
  视觉权重一致。判定＝**可接受**：severity 已由文案与通知系统自身的 `NotificationSeverity`
  （`lib/notifications.ts`，严重/警告/提示）承担，按 severity 改色需引入非 token 颜色。
- **开关型设置的「两级并存」**：通知偏好逐次静默（靠常驻说明「修改即时保存」），自动重启每次 toast。
  **判定域**：级别 1 只适用于**本地即时保存、无失败面**的偏好开关
  （`settings/components/notifications-panel.tsx`，纯 localStorage）；**服务端写、带失败面**的开关
  **不满足级别 1**——失败必须逐次可见 ⇒ 按**级别 2**给回执。故两者**不是同级不一致，而是同一
  判据下的不同级别**：`general-panel.tsx` 的自动重启（`apiUpdateInstance` + 失败回滚）与
  `webhooks/webhook-page.tsx` 的启停，其成功 toast 是级别 2 的**正确形态**（不是待删的冗余）；
  通知偏好的静默是级别 1 + 常驻说明的正确形态，不要为它补逐次 toast（一屏 20+ 开关会刷屏）。
